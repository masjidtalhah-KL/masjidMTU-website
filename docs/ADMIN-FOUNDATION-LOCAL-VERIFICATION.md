1. Actual Auth fixtures require the nil Auth instance UUID and non-null token
   string fields. The scripts now populate actual `auth.users`, identities,
   sessions and AMR records according to GoTrue's schema. These are disposable
   trusted-operator fixtures, never a runtime bootstrap or real Google login.
2. PostgREST 14.5 retried intentionally raised SQLSTATE `40001`, causing stale
   version RPCs to loop instead of returning a conflict. Intentional invite/member
   version conflicts now raise custom `PT409`, returning a terminal HTTP 409.

   HTTP tests now complete with one committed winner.

   with exact parity after newline normalization and no PGlite fallback. Optional `next_role` is

   generated `Relationships: []` is expected because its target is unexposed
   `auth.users`, outside `--schema public`; the FK itself exists and PostgREST's

## Auth hook: what was actually exercised

The main local Auth service is configured with
`pg-functions://postgres/private/before_user_created`. The actual
`supabase_auth_admin` database role can call it; client roles cannot. Positive
and negative event contracts were tested directly under that actual Auth role,
including exact pending Google email and expiry/revocation rejection.

For a genuine GoTrue invocation without enabling Google or public email signup
on the main service, the harness temporarily starts **the same GoTrue image**
against the same disposable DB on loopback port 54330. This isolated probe
enables email only to reach the hook's non-Google rejection branch. Actual Auth
`/signup` rejects both an uninvited email and an exact pending-invite email with
HTTP 403, even with spoofed provider/role metadata. No Auth user/profile is
created and the invitation is not consumed. The probe container and ignored
temporary environment file are removed in `finally`; the main configuration
continues to disable email/SMS/anonymous signup and Google.

**This proves local private-hook wiring and real GoTrue negative invocation.**
It does not prove the positive Google OAuth event emitted by hosted Auth.
Direct SQL positive-event testing is identified as a contract test, not a
successful OAuth flow. Real first-time Google admission, provider identity
fields and PKCE must pass staging before release.
[Hook contract](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook).

## Genuine local TOTP / AAL evidence

The initial synthetic Google identity and OAuth AMR are trusted local DB
fixtures. An isolated local Auth Admin link for that existing synthetic user
obtains a genuine Auth-issued AAL1 session/refresh token. The public providers
remain disabled; this is not verification of Google OAuth or public login.

The pinned SDK then performs genuine Auth TOTP enrollment, challenge and
verification for primary and backup factors. Auth issues the verified factors
and AAL2 JWT with numeric signed `totp` AMR. No verified TOTP factor or successful
TOTP response is fabricated. Invalid codes and replay of a consumed challenge
are rejected. Auth refresh preserves the TOTP evidence.

To test the boundary promptly, the operator fixture ages the Auth-owned AMR
timestamp by 660 seconds; this is an explicit clock fixture, not a ten-minute
wall-clock soak. Real Auth refresh issues the aged evidence: AAL2 reads remain
allowed, recent-MFA state becomes false and mutations return 403. A genuine
new challenge/verification plus refresh restores fresh proof and mutation
access. Removing both factors through actual local Auth Admin API makes the
still-valid old AAL2 JWT fail the live database owner gate.

The database 600-second check is therefore locally verified with real Auth
token/refresh semantics. Hosted Google sessions, factor policy/recovery and
deployment/session-plan controls remain staging gates. No TOTP seed is stored
in application tables or evidence files; secrets exist only in test memory.
[SDK challenge and verify](https://supabase.com/docs/reference/javascript/auth-mfa-challengeandverify).

## Reproduce locally

Use the pinned installed CLI, Docker Desktop Linux daemon and existing public
Sanity build environment. From the repository root:

```sh
npm run admin:local:start
npm run admin:local:reset
npm run build -- --webpack
npm run admin:local:test
npm run admin:types:check
npm run admin:db:test
npm run admin:policy:test
npm run admin:e2e
npm run lint
npx tsc --noEmit
npm run admin:bundle:check
git diff --check
```

The real test suite requires an empty disposable Auth/profile database and
fails closed if the configured local project/URLs/container do not match. Reset
before a repeat. Tests use only loopback endpoints; local keys are obtained into
memory from CLI/container configuration, never embedded in source or reports.
Build before the suite because the real SSR probe starts the production output.
Synthetic browser and real SSR probes stop their own application processes.

After verification, a final local reset reapplied the same migration and type
parity passed. Auth users, profiles, invitations and audit rows each count zero;
the normal local services remain running. No hook probe or test application is
left running. This clears disposable fixture data, not the application schema.
